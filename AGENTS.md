# Правила разработки

Инструкции распространяются на весь репозиторий. Идентификаторы пишем на английском,
документацию и комментарии — на русском.

## Работа над задачей

Читайте файлы и тесты затронутой области, а не весь проект. Проверяйте предположения по коду.
Сохраняйте существующие контракты; не добавляйте зависимости и абстракции без необходимости.
При изменении команд или соглашений обновляйте эту инструкцию.

## Имена

Имя объясняет роль: account, credentials, challengeID, challengeKey, otpNumber, err.
Не используйте однобуквенные имена, включая параметры, поля и receiver.
Исключения: t для *testing.T, b для *testing.B, i/j для индексов коротких циклов; _ допустим.
Receiver называйте по типу: service, server, store, worker; одинаково во всех методах типа.
HTTP-параметры называйте request и response. Не заменяйте смысловые имена общими data/value.
Понятные сокращения ctx, err, db, tx, id, ttl допустимы; составные имена — userID, otpTTL.
Имена внешних библиотек и generated-код не переименовывайте.
Правило проверяется при ревью, автоматической проверки нейминга нет.

## Стиль кода

После изменений запускайте make fmt: goimports → golines → gofumpt.
Лимит — 120 колонок, табуляция шириной 4. Импорты: standard, external, go-boilerplate.
Предпочитайте ранний возврат при ошибке и минимальную область видимости переменных.
Независимые этапы операции оформляйте отдельно; не связывайте их цепочкой проверок err == nil,
если это мешает чтению. Не меняйте обработку ошибок попутно с переименованием.
GoDoc экспортируемых сущностей начинается с имени и описывает контракт, ошибки,
побочные эффекты и владение ресурсами, когда это существенно.
Внутри реализации поясняйте причины и инварианты, а не очевидные действия.
Машинные директивы и generated-комментарии не переводите.

## Устройство и контракты

cmd собирает зависимости; httpapi содержит HTTP/Huma-контракты; auth — авторизацию;
accounts — изменения аккаунтов с аудитом; jobs — хранение задач и outbox;
usertasks — импорт/экспорт; worker — Kafka, таймеры и пул исполнения.
HTTP получает зависимости явно: не открывайте инфраструктуру через поля auth/jobs.
Прикладные ошибки не зависят от Huma; HTTP преобразует их и логирует причины один раз.
Общий контракт credentials находится отдельно от auth и используется HTTP и импортом.
Создание и закрытие инфраструктуры и служебных listeners остаётся в cmd.
Используйте типизированные контракты Huma и общую валидацию credentials.
Не добавляйте параллельную систему валидации или Swagger-комментариев.
SQL и sqlc определяют dbgen: generated-файлы вручную не редактируйте и не форматируйте.
После изменения исходного SQL выполняйте make generate и проверяйте результат.
Сохраняйте разделение user/admin, OTP, CSRF, ротацию и отзыв сессий.
Не раскрывайте секреты и внутренние поля в ответах и логах.
Сохраняйте транзакционность аудита/outbox, устойчивость к повторной доставке,
аренды задач и потоковую обработку файлов без загрузки целого файла в память.
Артефакты находятся в S3; jobs.directory содержит временные файлы текущего процесса.
Результаты разных попыток имеют уникальные ключи; ссылка публикуется при действующей аренде.
Не удаляйте объект немедленно при неопределённом исходе commit: очистка сверяет ссылки с БД.
Ошибка Pub/Sub после commit не меняет терминальный итог задачи.
Метрики используют registry процесса и ограниченные labels без ID, email и ключей файлов.

## Проверки

Команды выполняются из корня. Go и инструменты закреплены в go.mod.
Запускайте целевые тесты при работе и make check перед завершением:
форматирование, go vet, go test -race ./.... Не ослабляйте тесты ради прохождения.
make integration требует локальных сервисов Compose; тест изолирует БД, Redis и Kafka.
Не используйте рабочую инфраструктуру. Инструкции запуска — в README.md.
make loadtest и make loadtest-full запускайте только для соответствующих задач;
полный прогон может занимать часы. Новые тесты проверяют поведение, не факт переименования.
В отчёте указывайте выполненные проверки и причины пропусков.
