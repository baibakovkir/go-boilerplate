# Go boilerplate

Go API с пользовательской авторизацией, административным доступом через пароль
и email OTP, типизированной валидацией и OpenAPI, SMTP, аудитом и асинхронными
импортом/экспортом через Kafka. Интерфейса админки пока нет: API доступно через
Swagger UI и обычные HTTP-клиенты.

Обычные пользователи создаются **только административным импортом** CSV/XLSX.
Публичной регистрации и ручного создания пользователя через API нет.

## Быстрый запуск

Нужны Go 1.26.5+, Make и Docker Compose. Выполняй команды из корня проекта.

```sh
make dev
```

Одна команда создаёт личный `config/local.yaml`, если его ещё нет, поднимает
инфраструктуру, ждёт её готовности, выполняет миграции и seed, затем одновременно
запускает API и worker с hot reload. При ошибке подготовки приложения не запускаются.
Существующий личный конфиг и пароли администраторов не перезаписываются.

Process Compose объединяет логи с метками `api` и `worker`. Ctrl+C останавливает
оба наблюдателя Air и их дочерние приложения; на завершение отведено 30 секунд.
Дополнительный управляющий HTTP-сервер и автоматическое чтение `.env` отключены.
Если один Air завершается, менеджер останавливает второй. Ошибку сборки сам Air
показывает в логе и ждёт исправления исходников.

Docker-сервисы после Ctrl+C продолжают работать с сохранением данных:

```sh
make down
```

Для отдельного запуска по-прежнему доступны команды:

```sh
make setup  # Только инфраструктура, миграции и seed.
make api    # Только API с hot reload.
make worker # Только worker с hot reload.
```

Air следит за Go/YAML/HTML/SQL и пересобирает соответствующий процесс. Это
перезапуск приложения. Инструменты закреплены в `go.mod`, глобальная установка
и Node не требуются. Первый запуск может скачать и собрать Go-инструменты.

Без автоматического перезапуска:

```sh
go run ./cmd/app
go run ./cmd/worker
```

Адреса:

| Сервис | Адрес с хоста | Внутри Compose |
| --- | --- | --- |
| API и Swagger UI | http://localhost:8181/docs | Go работает на хосте |
| OpenAPI | http://localhost:8181/openapi.json | — |
| PostgreSQL | `localhost:25432` | `postgres:5432` |
| Redis | `localhost:26379` | `redis:6379` |
| Kafka | `localhost:29092` | `kafka:19092` |
| SMTP Mailpit | `localhost:21025` | `mailpit:1025` |
| Письма в Mailpit | http://localhost:28025 | `mailpit:8025` |

Docker публикует порты только на `127.0.0.1`. PostgreSQL, Redis и Kafka используют
выбранные ранее образы; Mailpit использует имеющийся `axllent/mailpit:latest`.
`pull_policy: missing` не обновляет имеющиеся образы автоматически.
Compose — локальное окружение: Kafka и Redis работают без TLS и аутентификации,
Mailpit принимает локальные письма без SMTP-пароля.
Теги Redis и Mailpit плавающие; на другой машине их версии могут отличаться.

Демонстрационный администратор из примера: `admin@example.test` / `admin123`.
Это локальные учебные credentials, не настройки для развёртывания.
`postgres/postgres`, база `boilerplate` — также локальные значения.

## Первый запрос: вход администратора и импорт

1. Открой `/docs`, выполни `POST /api/v1/admin/auth/login` с email и паролем.
2. Открой Mailpit, найди письмо с OTP. Передай `challenge_id` и код в
   `POST /api/v1/admin/auth/otp`.
3. В Swagger нажми **Authorize** и вставь полученный `access_token` без
   префикса `Bearer`. Refresh-cookie браузер сохранит автоматически.
4. Загрузи `examples/users.csv` через `POST /api/v1/admin/imports/{format}`,
   выбрав `csv`. Тело — файл, `Content-Type: application/octet-stream`.
5. Проверь `GET /api/v1/admin/jobs/{id}` или подпишись по WebSocket.

Через curl после получения access-токена:

```sh
export ACCESS_TOKEN='полученный-access-token'
curl -X POST http://localhost:8181/api/v1/admin/imports/csv \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H 'Content-Type: application/octet-stream' \
  --data-binary @examples/users.csv
```

Из примера создадутся Alice и Bob; остальные строки попадут в отчёт.
Повторный импорт существующие аккаунты не меняет. После создания Alice может
войти через `/api/v1/auth/login` с `alice@example.test` / `secret1`.

Для экспорта отправь `POST /api/v1/admin/exports`:

```json
{"format":"xlsx"}
```

Можно передать `email` (поиск подстроки) и `blocked` (`"true"`/`"false"`).
После завершения скачай `/api/v1/admin/jobs/{id}/download`.

## Типы, валидация и документация

Chi маршрутизирует запросы, Huma преобразует типизированные структуры ввода
и вывода в OpenAPI и проверяет входные данные до вызова обработчика.
Ограничения JSON и параметры пути/запроса документируются автоматически.
Неизвестные JSON-поля и query-параметры обычных Huma-методов отклоняются.

`auth.Credentials` описывает email и пароль один раз. Импорт использует
JSON Schema, построенную из этой же структуры. Правила пароля: **6–128
символов**, без обрезания пробелов или изменения регистра. Email нормализуется
в нижний регистр; в БД действует уникальность нормализованного email.

Структуры HTTP и БД разделены там, где отличаются данные. Хеши паролей,
версии авторизации, пути файлов и refresh-токены не входят в публичные модели.
`sqlc` генерирует запросы и типы результатов по SQL; `dbgen` вручную не меняем.

```sh
make generate
```

После изменения SQL выполняй генерацию и проверки. Для нового JSON-метода
достаточно зарегистрировать операцию Huma, описав вход и выход; отдельные
Swagger-комментарии и второй набор тегов валидатора не нужны.
Проверка уникальности и правильности текущего пароля выполняется сервисом.

Загрузка большого файла реализована отдельным потоковым HTTP-обработчиком,
чтобы не читать его целиком в память. Описание бинарного тела и результата
этого метода добавляется в OpenAPI явно. WebSocket описан ниже: OpenAPI
документирует выдачу билета, но не протокол кадров соединения.

Документация доступна во всех окружениях. `http_server.docs_allowed_cidrs: []`
означает отсутствие IP-ограничений. Чтобы ограничить её, задай, например,
`["127.0.0.1/32", "::1/128"]`; правило распространяется на Swagger UI,
его ресурсы и OpenAPI JSON/YAML.

## Авторизация и безопасность

У `users` и `admin_users` отдельные таблицы, способы входа, сессии и назначение
JWT. Один email может существовать в обеих таблицах. Все администраторы пока
имеют одинаковые полномочия. Пользовательский JWT не даёт доступа к admin API.

- Пароли — Argon2id с уникальной солью: 19 МиБ, 2 прохода, параллелизм 1.
- Access JWT — JSON-ответ; рекомендуем хранить его в памяти frontend и
  отправлять в `Authorization: Bearer ...`. Пользовательский действует
  15 минут, административный — 5 минут по умолчанию.
- Refresh — случайный секрет в HttpOnly cookie. Сервер хранит хеш; cookie
  пользователей и админов имеют разные имена и пути. Максимальная жизнь
  сессии — 30 дней и 8 часов соответственно, ротация её не продлевает.
- `/auth/refresh` заменяет refresh при каждом использовании. Повторное
  использование уже заменённого токена отзывает сессию. Клиент должен
  выполнять refresh последовательно, без параллельных запросов.
- Login/OTP/refresh возвращает `csrf_token`. Для refresh/logout передавай его
  в `X-CSRF-Token`. После перезагрузки страницы его можно получить через
  соответствующий `GET /auth/csrf`, используя refresh-cookie.
- Выход отзывает текущую сессию. Смена/восстановление пароля, блокировка и
  административный отзыв сессий изменяют версию авторизации в БД. Middleware
  проверяет её и Redis-сессию, поэтому старый access теряет доступ сразу.
- Смена пароля требует текущий пароль и завершает все сессии аккаунта.
  Восстановление отправляет одноразовый токен через SMTP; токен вводится
  вместе с новым паролем через API. Готового frontend со страницей сброса нет.
- OTP администратора действует 5 минут, имеет 5 попыток; повторная отправка
  доступна через минуту. Публичного создания администраторов нет.
- Импортированные пользователи сразу допускаются к входу; подтверждение
  email и приглашения при импорте не отправляются.

CORS разрешает только origins из YAML и включает credentials. `*` не
используется. Сервер дополнительно проверяет Origin, а WebSocket — Origin и
одноразовый билет. По умолчанию cookies `SameSite=Lax`: frontend предполагается
на том же site (локальные порты могут различаться).

Rate limiter хранит счётчики в Redis: общий лимит 300 запросов/минуту на IP,
30 чувствительных POST-запросов/минуту на IP, 10 попыток входа/15 минут на
аккаунт, 3 запроса письма восстановления/15 минут на аккаунт. Загрузки —
2/минуту на IP, экспорт — 5/минуту на админа, билеты — 20/минуту на сессию.
При недоступности Redis защищённые операции возвращают 503, без обхода защиты.

`trusted_proxies` по умолчанию пуст: `X-Forwarded-For` от произвольного клиента
не считается источником IP. При явно доверенных прокси цепочка проверяется
справа налево. Нельзя безусловно доверять левому значению заголовка.

Тела JSON ограничены 64 КиБ, HTTP-заголовки — 32 КиБ. Для файлов действуют
отдельные лимиты и дедлайны. SQL параметризован; просмотр таблиц ограничен
разрешёнными проекциями. Строки CSV/XLSX экспорта не исполняются как формулы.
Ответы об ошибках — `application/problem+json`; ошибки валидации не отражают
значения полей. В логи не пишутся пароли, токены, OTP или тела запросов.

Вне `local` конфиг требует Secure cookies, замену демонстрационного JWT-секрета
и TLS для SMTP. HTTPS должен обеспечиваться сервером перед API; его origin
нужно явно разрешить в конфиге. IP-ограничение docs само по себе не заменяет
авторизацию административных методов.

## Общая схема задач

`jobs` хранит жизненный цикл любой операции. Импорт и экспорт пользователей —
демонстрационные обработчики в `internal/usertasks`; worker выбирает обработчик
из реестра и не содержит условий «импорт или экспорт».

| Таблица | Назначение |
| --- | --- |
| `jobs` | Тип, статус, автор, прогресс, аренда, повторы и общие JSONB-данные |
| `job_issues` | Диагностика элементов: ключ элемента, severity, code и произвольный `error jsonb` |
| `outbox` | Надёжная передача идентификатора задачи в Kafka |
| `audit_logs` | История действий с типизированными автором, действием и результатом |

`type`, `status`, коды ошибок, severity и категории аудита заданы PostgreSQL enum.
Допустимые значения можно посмотреть в БД, например:

```sql
SELECT enum_range(NULL::job_type);
SELECT enum_range(NULL::job_status);
SELECT enum_range(NULL::job_error_code);
```

SQL — источник вариантов: sqlc генерирует Go-типы, `Valid()` и списки значений;
OpenAPI использует эти списки, а не отдельные копии в тегах валидатора.

У автора два nullable FK: `created_by_user_id` и `created_by_admin_id`.
CHECK запрещает заполнить оба; оба пусты у системной задачи. Отдельная таблица
задач для пользователей не нужна. Админ видит задачи всех авторов, пользователь
только свои — в REST, отчётах, скачивании и WebSocket.

`data jsonb` содержит общий контейнер без колонок `filter_email`, `source_path`
и подобных деталей демонстрации:

```json
{
  "input": {"format": "csv", "email": "example.test"},
  "checkpoint": {"rows": 500},
  "files": [{"role": "result", "key": "UUID.result.csv", "format": "csv", "name": "users.csv"}],
  "result": {"format": "csv", "count": 500}
}
```

Это пример структуры контейнера; содержимое `input`, `checkpoint` и `result`
определяет обработчик. Формат и роль файла используют сгенерированные enum-типы.
Публичное состояние включает только `result`: параметры, checkpoint и ключи файлов
клиенту не выдаются. Ошибка всей задачи хранится в `error_code` и `error jsonb`.

В `job_issues` нет колонок email и номера строки. У импорта контекст ошибки
может быть `{"row_number": 7, "email": "alice@example.test"}`, у другой операции —
другим JSON-объектом. Отдельные записи позволяют выдавать миллион ошибок
постранично, не накапливая огромный JSON-массив в одной записи `jobs`.

Чтобы подключить операцию, добавь её в SQL enum `job_type`, сгенерируй типы и
зарегистрируй обработчик через `Service.Register` в точке сборки приложения.
Обработчик получает контекст, задачу и идентификатор аренды. Параметры проверяет
сам модуль. Прикладной endpoint проверяет право запуска и вызывает общий `Create`:
системный автор — `Actor{}`, пользовательский/административный — из проверенной сессии.
Публичного endpoint, запускающего произвольный тип по строке клиента, нет.

Административные маршруты остаются под `/api/v1/admin/jobs` и `/api/v1/admin/ws*`.
Для пользователей доступны `/api/v1/jobs`, `/api/v1/jobs/{id}`,
`/api/v1/jobs/{id}/errors`, `/download`, `/report`, `/api/v1/ws-tickets`, `/api/v1/ws`.
Создание пользовательских задач добавляется конкретной прикладной функцией;
демонстрационный импорт/экспорт всех пользователей остаётся административным.

## Фоновые задачи и WebSocket

API сохраняет файл с серверным именем, создаёт `jobs` и `outbox` в одной
транзакции БД. Worker отправляет ID задачи в Kafka и подтверждает outbox
после успешной публикации. Если Kafka недоступна, задача остаётся в БД.
Файл и пароли не отправляются через Kafka.

Worker захватывает сохраняемую в PostgreSQL аренду задачи и продлевает её.
Kafka-offset подтверждается после передачи задания в обработку; восстановление
после сбоя обеспечивают аренда, outbox и сохранённая позиция. Повторная
доставка завершённой или уже занятой задачи не создаёт второй результат.
Один worker одновременно обрабатывает одну задачу. API и worker используют
одинаковые БД, Redis, тему Kafka и директорию файлов.

Импорт:

- CSV UTF-8 с запятой или XLSX с одним листом. Первый ряд строго
  `email,password`, в таком порядке. CSV-запись занимает одну физическую
  строку, максимум 64 КиБ; многострочные поля не поддерживаются.
- Предварительный потоковый проход проверяет заголовок, читаемость и лимит
  строк. Некорректный контейнер/синтаксис завершает задачу с кодом ошибки.
- До миллиона строк, загрузка до 512 МиБ, распаковка XLSX до 2 ГиБ.
- Корректные строки хешируются ограниченным числом обработчиков и сохраняются
  пакетами по 500. Ошибочные и существующие email пропускаются с отчётом.
- В БД одной транзакцией пакета фиксируются пользователи, общая диагностика и checkpoint в `data`.
  При повторном запуске уже сохранённые пакеты не обрабатываются заново.
- Статусы: `queued`, `running`, `completed`, `completed_with_errors`, `failed`.
  Повторяемые ошибки получают задержку и ограничение числа попыток.
- Ошибки доступны постранично через `/jobs/{id}/errors` и CSV-отчётом
  `/jobs/{id}/report`. Паролей в отчёте нет. CSV-отчёт содержит `item_key`, `code` и `error` (JSON-контекст).

Экспорт использует согласованный снимок PostgreSQL и потоковую запись CSV/XLSX
на диск. При повторной попытке строится новый снимок и файл заново. Частично
готовый результат не доступен для скачивания. Максимум — миллион записей;
при превышении задача завершается с `row_limit_exceeded`.

WebSocket:

1. Вызови `POST /api/v1/admin/ws-tickets` с `{"job_id":"UUID"}` и admin Bearer.
2. Подключись к пути `url` из ответа, заменив схему HTTP на WS (HTTPS на WSS).
   Билет действует 30 секунд и используется один раз.
3. Сервер сразу отправит снимок и затем обновления:

```json
{
  "type": "job.progress",
  "job": {
    "id": "UUID",
    "type": "users.import",
    "status": "running",
    "processed": 500,
    "succeeded": 490,
    "failed": 10,
    "total": 1000,
    "version": 4,
    "attempts": 1,
    "artifacts_expired": false,
    "created_at": "2026-10-22T12:00:00Z",
    "updated_at": "2026-10-22T12:00:01Z"
  }
}
```

Одно соединение подписано на одну задачу. Клиентские сообщения не требуются.
Обновления отправляются не чаще раза в секунду. PostgreSQL — источник
состояния, Redis Pub/Sub — уведомления; раз в 5 секунд состояние дополнительно
сверяется с БД. Пропущенное Pub/Sub-сообщение не теряет результат.

На переподключение нужен новый билет. Соединение закрывается при истечении
access JWT, остановке сервера или отзыве сессии (при следующей проверке,
не позднее 5 секунд). После refresh получи новый билет. REST `/jobs/{id}`
остаётся доступным способом проверки. Одновременно API допускает 128 WS-соединений.

Файлы лежат в `jobs.directory` (по умолчанию `var/jobs`, вне Git).
Исходники с паролями удаляются после завершения задачи; периодическая очистка
также подбирает их после аварийного завершения. Результаты/отчёты хранятся
7 дней. Потерянные загрузки и временные файлы с ID задачи очищаются через сутки,
если больше не относятся к активной задаче или сохраняемому результату.
Задачи и их итоговые метаданные остаются в БД. S3-хранилище пока не подключено.

## Аудит, диагностика и просмотр данных

В `audit_logs`: время, исполнитель, действие, объект, результат и request ID.
Пишутся входы/выходы, операции с паролями, блокировка/отзыв сессий, запуск и
завершение задач, просмотр административных проекций. Импорт получает сводные
события; подробности строк хранятся отдельно.

По умолчанию аудит хранится 90 дней, очистка выполняется ежедневно в 03:00 UTC.
`audit.schedule` — cron из пяти полей; для первого числа месяца:
`"0 3 1 * *"`. При месячном расписании записи могут храниться дольше заданного
срока до ближайшей очистки. PostgreSQL advisory lock предотвращает одновременную
очистку несколькими worker. Удаление идёт небольшими пакетами.

`GET /api/v1/admin/tables` показывает разрешённые таблицы. Просмотр
`/tables/{table}` возвращает только безопасные проекции `users`, `jobs`,
`audit_logs`, с пагинацией. `admin_users`, хеши и внутренние пути недоступны.
Произвольного SQL и редактирования внутренних таблиц нет.

`GET /api/v1/admin/kafka` показывает топики, партиции, лидеров/реплики,
consumer groups и lag. Сообщения и настройки Kafka через API не изменяются.

Технические ошибки пишутся отдельно через `slog`: цепочка причины, операция,
request ID или job ID; для panic — стек. Локально логи текстовые, в dev/prod —
JSON. Логи выводятся в stdout; срок их хранения задаётся окружением запуска,
очистка аудита их не затрагивает.

`/health/live` проверяет, что API отвечает. `/health/ready` проверяет PostgreSQL
и Redis; Kafka не включена в готовность API, поскольку outbox допускает её
временную недоступность. Миграции выполняются явно до старта API.

## Конфигурация и структура

Обычному запуску не нужен `CONFIG_PATH`: читается `config/local.yaml`.
Переменная нужна только для другого пути. `cleanenv` читает YAML, применяет
значения по умолчанию и переопределения окружения; `.env` автоматически не читается.
Приоритет: окружение → YAML → значения по умолчанию.

Переменные окружения: `APP_ENV`, `HTTP_ADDRESS`, `POSTGRES_HOST`,
`POSTGRES_PORT`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`,
`POSTGRES_SSLMODE`, `REDIS_ADDRESS`, `REDIS_PASSWORD`, `KAFKA_BROKERS`
(через запятую), `JWT_SECRET`, `COOKIE_SECURE`, `SMTP_HOST`, `SMTP_PORT`,
`SMTP_USERNAME`, `SMTP_PASSWORD`, `JOBS_DIRECTORY`. Остальные параметры — YAML.

- `cmd/app` — HTTP API и корректное завершение сервера.
- `cmd/worker` — Kafka, фоновые задачи, восстановление и периодическая очистка.
- `cmd/migrate` — SQL-миграции и создание админов из YAML.
- `internal/config` — загрузка и проверка настроек.
- `internal/auth`, `security`, `mail` — авторизация, ограничения и SMTP.
- `internal/httpapi` — маршруты, типы HTTP, middleware, Swagger и WS.
- `internal/jobs`, `worker` — общий механизм задач, аренды, повторы и файлы.
- `internal/usertasks` — демонстрационные импорт и экспорт пользователей.
- `internal/database/migrations`, `queries` — SQL; `dbgen` — код sqlc.

В `go.mod` закреплены зависимости приложения, Air, sqlc, Process Compose и инструменты форматирования.
Большая часть `// indirect` относится к зависимостям этих инструментов.
`go mod tidy` синхронизирует их; `gofmt` форматирует Go-код и импорты.

`make migrate` никогда не меняет пароль уже существующего админа. Для обычной
смены используй административный `/me/password`, для восстановления — его
SMTP-сценарий. Правка исходного пароля в YAML не сбрасывает пароль в БД.

Настройки `POSTGRES_*` в Compose относятся к контейнеру и не становятся
окружением Go-процессов. Они применяются PostgreSQL при создании пустого volume;
редактирование Compose не меняет пароль уже инициализированной БД.

## Оформление кода и комментарии

```sh
make fmt       # Применить оформление.
make fmt-check # Проверить без изменения файлов.
make lint      # Оформление и go vet.
make check     # Всё перечисленное и тесты с детектором гонок.
```

Лимит написанного вручную Go-кода — **120 колонок**. Табуляция отображается
шириной 4; русские символы считаются символами, а не байтами UTF-8.
`.editorconfig` задаёт эти настройки для редакторов.

Команда `cmd/style` последовательно применяет `goimports`, `golines` и `gofumpt`.
Импорты разделены на стандартную библиотеку, внешние зависимости и пакеты
`go-boilerplate`. Необычные длинные выражения, SQL, комментарии и строковые
литералы при необходимости разбиваются вручную; проверка сообщает файл и строку.
Длинные значения строк сохраняются конкатенацией, SQL — переносами пробелов.
HTML Swagger встроен из `internal/httpapi/docs.html`.

Файлы с меткой `Code generated ... DO NOT EDIT.` пропускаются: содержимое `dbgen`
определяет sqlc, ручное форматирование генерации не применяется.

Комментарии пишем на русском в формате GoDoc. У экспортируемых типов и функций
описываем назначение и существенный контракт: ошибки, побочные эффекты, владение
ресурсами. Комментарий начинается с имени сущности; описание пакета — с
`Package` и его имени. Названия технологий и идентификаторы сохраняются.
Внутри реализации поясняем причины и инварианты: границы транзакций, отзыв сессий,
аренды, повторную доставку и защиту файлов. Очевидные действия построчно не описываем.
Машинные директивы и сгенерированные комментарии не переводятся.

## Проверки

```sh
make test
make check
make integration
make loadtest
```

`integration` требует работающий Compose. Тест создаёт отдельную временную БД,
Redis-префикс и Kafka-топик, отправляет тестовые письма через Mailpit, затем
удаляет свои БД/ключи/топик. Рабочие таблицы и задачи проекта не используются.
Проверяются OTP, сессии, CSRF, отзыв доступа, outbox при недоступной Kafka,
продолжение импорта после сбоя, WS, CSV/XLSX, безопасные проекции и очистка.

`loadtest` проверяет потоковую запись/чтение миллиона строк CSV и XLSX с
измерением Go heap, без миллиона хеширований. Полная цепочка с реальными
Argon2id, Kafka и БД запускается отдельно:

```sh
make loadtest-full
```

Она может занять часы и требует ресурсов для миллиона тестовых пользователей;
в обычный набор тестов не входит. Скорость парсеров не равна скорости импорта
паролей. Отдельный замер хеширования:

```sh
go test ./internal/security -run '^$' -bench BenchmarkPasswordHash -benchtime=10x
```

Управление инфраструктурой:

```sh
docker compose ps
docker compose logs -f kafka
docker compose exec postgres psql -U postgres -d boilerplate
docker compose exec redis redis-cli ping
docker compose down
```

`down` сохраняет данные. `docker compose down -v` удаляет volumes проекта
**со всеми данными**, включая БД и письма Mailpit.
