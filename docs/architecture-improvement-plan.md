# План развития архитектуры go-boilerplate

План основан на статическом анализе текущего кода. Это последовательность
доработок существующего приложения, а не предложение переписать его на Clean
Architecture. Примеры ниже показывают целевой интерфейс; они не являются готовыми
патчами. При выполнении каждого этапа нужно сверять контракты с актуальным кодом.

## Цель и ограничения

Сохранить функциональные пакеты, явную сборку приложения в `cmd`, sqlc,
транзакционное создание задач через outbox и разделение `jobs` / `usertasks`.
Усилить границы так, чтобы HTTP отвечал за протокол, прикладные сервисы — за
операции и транзакции, инфраструктура — за взаимодействие с внешними системами.

По умолчанию сохранить маршруты, JSON-контракты, правила авторизации, атомарность
аудита и поведение фоновых задач. Не добавлять абстракцию на каждую таблицу,
универсальный CRUD-репозиторий, DI-фреймворк или новые сервисы инфраструктуры.

## Очерёдность

| Этап | Приоритет | Результат | Зависимости |
| --- | --- | --- | --- |
| 0. Зафиксировать исходное поведение | P0 | Воспроизводимые проверки и перечень контрактов | Нет |
| 1. Прикладные ошибки | P1 | `auth` не зависит от Huma | 0 |
| 2. Сервис административных операций | P1 | Изменения пользователей и аудит вынесены из HTTP | 1 |
| 3. Явные зависимости HTTP | P1 | Нет доступа к общей БД через `Auth.DB` | 2 |
| 4. Границы ядра задач | P2 | Worker координирует выполнение, хранилище инкапсулирует SQL | 0, затем согласовать с 3 |
| 5. Проверить гарантии при отказах | P1 | Ключевые сценарии восстановления подтверждены тестами | 0; повторить затронутое после 4 |
| 6. Диагностика и готовность | P2 | Причины задержек и деградации различимы | 3–5 |
| 7. Распределённый запуск | Условно | Общие артефакты и контролируемая параллельность | Только при реальной потребности |

P0 — подготовка к безопасным изменениям. P1 — ближайшая работа. P2 — следующий
этап. Этап 5 стоит начать до рефакторинга задач: сначала проверить существующие
гарантии, затем менять реализацию. Каждый этап выполнять отдельным PR; крупный
этап разбивать на несколько совместимых изменений.

## 0. Зафиксировать исходное поведение

**Где:** `Makefile`, `internal/httpapi/integration_test.go`, существующие тесты.

**Проблема:** обычный `go test ./...` не подтверждает работоспособность цепочки
PostgreSQL → outbox → Kafka → worker: интеграционный тест включается отдельно.
При изменении архитектуры легко сохранить компиляцию и нарушить поведение.

**Действия:**

1. Выполнить `make check` и, в изолированном окружении Compose, `make integration`.
2. Записать исходные результаты и отдельно указать пропущенные проверки.
3. Проверить существующее покрытие блокировки пользователя, отзыва сессий,
   аудита, восстановления задач и доступа к артефактам. Дополнять только пробелы.
4. Зафиксировать значимые внешние контракты: статусы ошибок, поля ответов,
   cookie/CSRF, право чтения задач и закрытые поля `jobs.Data`.

Не использовать рабочую БД для интеграционных проверок. Перед автоматизацией
проверить, как тест создаёт, очищает и изолирует данные.

**Готово, когда:** исходные проверки воспроизводимы, известные сбои описаны,
а последующие PR можно сравнивать с одной исходной точкой.

## 1. Отделить прикладные ошибки от Huma

**Где:** `internal/auth/service.go`, `internal/httpapi/server.go`, обработчики API.

**Сейчас:** `auth.Service` возвращает `huma.Error*`; `Failure` логирует внутреннюю
причину и возвращает HTTP-ошибку 503. Повторное использование сервиса вне HTTP
тянет зависимость от транспортного фреймворка.

**Изменение:** определить небольшой набор прикладных кодов ошибок и преобразовать
их в Huma только в `httpapi`. Коды вводить по существующим сценариям, сохраняя
различия между 400, 401, 403, 404, 409, 429 и 503 там, где они уже используются.
Не сводить все ошибки входа к одному коду с другим HTTP-статусом.

Пример для недоступности зависимости:

```go
// internal/apperror/errors.go
type Code string

const Unavailable Code = "unavailable"

type Error struct {
    Code  Code
    Op    string
    Cause error
}

func (appError *Error) Error() string { return string(appError.Code) }
func (appError *Error) Unwrap() error { return appError.Cause }
```

Сервис возвращает `&apperror.Error{Code: apperror.Unavailable, Op: "load account",
Cause: err}`. HTTP-адаптер извлекает ошибку через `errors.As`, пишет внутреннюю
причину с request ID и отдаёт клиенту обезличенное сообщение. Причину нельзя
сериализовать в ответ. Для ошибок валидации нужен отдельный безопасный контракт
полей, если текущий API его предоставляет.

**Порядок:** добавить типы и адаптер; перевести одну операцию; проверить её
контракт; перевести остальные. Выбрать одну точку логирования ошибки, чтобы
не записывать один сбой одновременно в сервисе и HTTP.

**Проверка:** табличные тесты преобразования кодов в HTTP; тест отсутствия
SQL/Redis-ошибок и секретов в ответах; существующие проверки авторизации.

**Готово, когда:** `internal/auth` не импортирует Huma, HTTP-контракты сохранены,
исходную техническую причину можно найти в логе.

## 2. Вынести административные изменения из HTTP

**Где:** `internal/httpapi/admin.go` → новый пакет `internal/accounts`.

**Сейчас:** обработчики блокировки и отзыва сессий сами открывают транзакцию,
изменяют пользователя и добавляют аудит. Правила операции принадлежат HTTP.

**Изменение:** добавить прикладной сервис с двумя явными операциями:

```go
type Actor struct {
    AdminID   uuid.UUID
    RequestID string
}

func (service *Service) SetBlocked(
    ctx context.Context, actor Actor, userID uuid.UUID, blocked bool,
) error

func (service *Service) RevokeSessions(
    ctx context.Context, actor Actor, userID uuid.UUID,
) error
```

HTTP извлекает проверенного администратора из контекста и формирует `Actor`.
Идентификатор автора не берётся из тела запроса. Политика допуска к операции
должна быть явной: HTTP проверяет роль; другие вызывающие стороны обеспечивают
эквивалентную проверку. Одна структура `Actor` не доказывает наличие полномочий.

На первом шаге сервис может использовать конкретный `database.Store`. Важнее
перенести целую операцию вместе с транзакцией, чем сразу вводить репозитории.

В одной транзакции остаются:

1. Изменение пользователя и версии авторизации согласно текущим SQL-запросам.
2. Проверка отсутствующего пользователя по числу изменённых строк.
3. Запись аудита с автором и request ID.
4. Commit только после успешного выполнения всех шагов.

Не заменять механизм отзыва простой очисткой Redis: нужно сохранить существующую
проверку версии аккаунта. Поведение уже выпущенного JWT и открытого WebSocket
проверить отдельно.

**Проверка:** реальный PostgreSQL: изменение и аудит фиксируются вместе; ошибка
аудита откатывает изменение; отсутствующий пользователь даёт прежний ответ;
старые сессии теряют доступ согласно действующему контракту.

**Готово, когда:** обработчики этих операций содержат разбор запроса, вызов сервиса
и преобразование результата; транзакций и SQL в них нет.

## 3. Убрать скрытый доступ к инфраструктуре из HTTP

**Где:** `internal/httpapi/server.go`, `admin.go`, `jobs.go`, `cmd/app/main.go`.

**Сейчас:** задачи, аудит и списки пользователей читаются через `s.Auth.DB`.
Изменение устройства авторизации затрагивает несвязанные endpoints.

**Изменение:** передавать HTTP необходимые операции явно:

```go
type Dependencies struct {
    Auth     *auth.Service
    Accounts *accounts.Service
    Jobs     *jobs.Service
    Queries  Queries
    Health   HealthChecker
}
```

`Queries` здесь — эскиз. При реализации выбрать небольшие интерфейсы чтения
пользователей, аудита и задач либо конкретные query-сервисы. Не собирать все
операции приложения в один большой интерфейс. Чтение без бизнес-правил можно
делегировать sqlc напрямую через отдельную зависимость; для него не нужен
обязательный дополнительный use case.

Проверки доступа к задачам должны остаться явными и едиными для REST, WebSocket
и скачивания файлов. Перенос чтения не должен открыть закрытые поля `Input`,
`Checkpoint`, ключи файлов или параметры аренды.

Клиент Kafka, который сейчас создаётся в `httpapi.New`, передавать как нужную
операцию проверки зависимости либо готовый клиент с документированным владельцем.
Сначала уточнить его реальные использования; если он не нужен HTTP — удалить.
Создание и закрытие ресурсов сосредоточить в `cmd`.

После миграции потребителей закрыть поля `auth.Service` и предоставить только
нужные методы. Поля `jobs.Service` закрывать после этапа 4.

**Проверка:** сохранить существующие проверки прав и публичных ответов;
проверить запуск и завершение приложения после изменения владения ресурсами.

**Готово, когда:** в `httpapi` нет `s.Auth.DB`, `s.Auth.Redis` и `s.Auth.Config`;
набор зависимостей виден из конструктора; каждый ресурс закрывает один владелец.

## 4. Усилить границы механизма задач

**Где:** `internal/jobs/service.go`, `internal/worker/worker.go`,
`internal/usertasks/tasks.go`, `import.go`, `export.go`.

**Сейчас:** разделение ядра и предметных обработчиков уже есть, но `worker`
выполняет SQL через `w.Jobs.DB`, а `usertasks.Handlers` встраивает `*jobs.Service`
и получает доступ ко всей инфраструктуре.

**Изменение в два шага:**

1. Перенести SQL диспетчеризации outbox, восстановления и очистки в явные методы
   хранилища или сервиса задач. Worker оставляет таймеры, Kafka, конкурентность,
   остановку и вызов операций. Границы транзакций переносить целиком.
2. Заменить встраивание `*jobs.Service` именованными зависимостями. Выделить
   ограниченный интерфейс прогресса/завершения задачи и отдельный доступ к данным
   пользователей. Не прятать весь прежний сервис за интерфейсом такого же размера.

Пример направления:

```go
type Handlers struct {
    jobs  JobRuntime
    users *database.Store // сначала допустима конкретная зависимость
}
```

Отделить сохранение результата от уведомления: commit в PostgreSQL и ошибка
Redis Pub/Sub — разные исходы. Проверить текущую связку `Finish` и `process`:
сбой уведомления после commit не должен запускать повтор предметной операции.
Ошибка уведомления логируется; сохранённый результат доступен через REST и
существующий механизм синхронизации WebSocket, который нужно проверить тестом.

Не обещать exactly-once. Аренды и доставка сообщений допускают повторное
выполнение; предметный обработчик должен безопасно возобновлять работу.
Добавление нового типа задачи сейчас включает enum/схему БД и регистрацию
обработчика — это приемлемый явный контракт, его стоит документировать.

**Проверка:** контрактные интеграционные сценарии из этапа 5 до и после переноса.
Моки SQL не заменяют проверку транзакций и конкурентного захвата в PostgreSQL.

**Готово, когда:** worker не обращается к `Jobs.DB.Pool`; обработчики не получают
весь сервис через embedding; новый учебный тип задачи не требует изменения
цикла worker; ошибка Pub/Sub не меняет терминальный исход задачи.

## 5. Подтвердить гарантии при отказах

**Где:** существующий интеграционный набор; при росте выделить отдельный набор
для `jobs`/`worker`, сохранив сквозные проверки HTTP.

Сначала сопоставить таблицу с уже существующими тестами. Добавлять недостающие
сценарии и утверждения, а не дублировать имеющееся покрытие.

| Сценарий | Ожидаемая гарантия |
| --- | --- |
| Kafka недоступна после создания задачи | Задача и outbox сохранены; после восстановления публикация продолжается |
| Публикация успешна, удаление outbox не закоммичено | Повторное сообщение не повреждает результат |
| Worker потерял аренду | Устаревший владелец не сохраняет прогресс или итог поверх нового |
| Worker остановлен между порциями импорта | Checkpoint позволяет продолжить без повторных побочных эффектов |
| Redis недоступен после commit результата | Итог остаётся терминальным и читается после восстановления доступа |
| Два worker захватывают одну задачу | Только один актуальный владелец проходит защищённое обновление |
| Пользователь заблокирован во время WebSocket | Соединение теряет доступ согласно контракту отзыва |
| Загрузка файла завершилась, транзакция создания не прошла | Файл удалён либо доступен предсказуемой очистке после аварии |

Для аварий между шагами использовать управляемые точки отказа в тестовом
адаптере или отдельные процессы. Не полагаться на случайный `sleep` и совпадение
таймингов. Проверять состояние БД и артефактов, а не только наличие записи в логе.

**Готово, когда:** для каждой гарантии есть тест или явно описанное ограничение;
повторный запуск не оставляет зависших задач и чужих тестовых данных.

## 6. Сделать деградацию наблюдаемой

**Где:** `internal/httpapi/server.go`, `internal/worker/worker.go`, логирование.

**Сейчас:** readiness API проверяет PostgreSQL и Redis. Создание задачи и её
исполнение имеют разные зависимости: Kafka может быть недоступна, но outbox
позволяет принять задачу. Нельзя автоматически объявлять весь API неготовым
при любом сбое брокера.

**Действия:**

- Описать контракт: liveness — процесс работает; readiness API — может безопасно
  обслуживать заявленный набор запросов; отдельное состояние фонового конвейера —
  задачи исполняются или накапливаются. Возвращать минимальные публичные детали.
- Добавить показатели: число и возраст queued-задач, возраст старейшей записи
  outbox, длительность задач, повторы, потеря аренды, ошибки публикации и Pub/Sub.
- Дополнить структурированные логи полями `job_id`, `job_type`, `attempt`,
  `lease_owner`, где применимо. Не писать токены, пароли и содержимое импорта.
- Выбирать пороги оповещений по допустимому времени ожидания задачи и измерениям,
  а не по произвольным универсальным значениям.

**Пример:** рост возраста outbox при живом API указывает на задержку доставки;
running-задачи с истёкшей арендой — на проблемы исполнителей или восстановления.

**Готово, когда:** при отключении Kafka видны накопление задач и причина задержки;
при восстановлении видно сокращение очереди. Новое средство сбора метрик выбирать
под окружение развёртывания, не вводить ради самого этапа.

## 7. Подготовить распределённый запуск при необходимости

**Условие начала:** API и worker действительно нужно запускать на разных узлах
или требуется больше одного исполнителя. Для локального шаблона этап необязателен.

### 7.1. Артефакты

Сейчас артефакты сохраняются в локальную директорию задач. Отдельным узлам нужен
общий том либо объектное хранилище. На первом шаге документировать требование
общего тома. Объектный адаптер вводить при необходимости независимого размещения.

Пример минимального контракта:

```go
type ArtifactStore interface {
    Put(ctx context.Context, key string, src io.Reader) error
    Open(ctx context.Context, key string) (io.ReadCloser, error)
    Delete(ctx context.Context, key string) error
}
```

Отдельно определить атомарность публикации файла, лимиты, повторную загрузку,
политику очистки осиротевших объектов и семантику удаления отсутствующего ключа.
Авторизация скачивания остаётся прикладной операцией, знание ключа не даёт доступ.

### 7.2. Параллельность

Worker сейчас ограничен одной одновременно исполняемой задачей. Перед увеличением
параллельности измерить память при XLSX, стоимость хеширования паролей, загрузку
PostgreSQL и доступное число соединений. Затем добавить конфигурируемый лимит
и проверить несколько задач, остановку и конкуренцию нескольких процессов.

Не увеличивать число обработчиков только потому, что Kafka допускает больше
потребителей. Сначала определить лимит ресурсов на один импорт/экспорт.

**Готово, когда:** файл, созданный API на узле A, доступен worker на узле B;
два worker безопасно исполняют разные задачи; остановка не оставляет
невосстанавливаемого состояния; потребление ресурсов укладывается в бюджет.

## Проверки для каждого PR

- `make check` — форматирование, vet и тесты с race detector.
- `make integration` — для изменений auth, транзакций, jobs, worker и HTTP-контрактов;
  инфраструктуру поднимать отдельно в изолированном окружении.
- `make generate` и проверка diff — только при изменении SQL/настроек sqlc.
- Нагрузочные проверки — при изменении алгоритма импорта, памяти или конкурентности.
  Миллион строк с реальным хешированием не требуется для каждого рефакторинга.

Если появится CI, разделить быстрые проверки и интеграционный job. Интеграционный
job должен явно включать `RUN_INTEGRATION=1`; успешный job с пропущенным тестом
не считается проверкой конвейера. Добавить явный таймаут выполнения с запасом
по измеренной длительности; сейчас цель `integration` его не задаёт.

## Что пока оставить без изменений

- Структуру по функциональным пакетам: не создавать зеркальные деревья
  `domain/usecase/repository` для каждого небольшого модуля.
- sqlc и `dbgen` внутри реализации хранения. Отдельные DTO вводить на устойчивых
  публичных границах и там, где они скрывают закрытые поля, а не для каждого запроса.
- Существующие Kafka и Redis: не заменять инфраструктуру одновременно с переносом
  ответственности между пакетами. Отдельная оценка необходимости брокера возможна
  позже с учётом требований; текущий план не требует новых брокеров или кешей.
- `mail.Sender`: узкий интерфейс отправки писем уже существует и подходит для подмены.

## Первый PR

После фиксации исходных проверок взять одну операцию — блокировку пользователя:
добавить необходимые прикладные ошибки и их HTTP-преобразование, создать
`accounts.Service.SetBlocked`, перенести транзакцию вместе с аудитом, внедрить
сервис в HTTP и проверить прежний ответ и отзыв доступа. Такой PR проверяет
направление архитектуры на реальном сценарии и остаётся небольшим для ревью.
